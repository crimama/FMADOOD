# DINOv3 intermediate normalization diagnostic

Registered 2026-09-29 before inspecting public-query metrics.

## Question and hypothesis

Does applying the DINOv3 model's final LayerNorm to selected intermediate
block features change RSG4 performance on MVTec AD 2's public development
queries? The hypothesis is that normalization may improve the calibration and
fusion of the selected intermediate feature layers; a metric difference alone
will not establish that normalization caused the observed behavior.

## Matched comparison

- Baseline: current `outputs.hidden_states[layer + 1]` extraction.
- Candidate: apply the frozen HF model's `norm` LayerNorm to non-final selected
  hidden-state slots. HF Transformers 4.56.2 places its already-normalized
  `last_hidden_state` in the final hidden-state slot, so layer 23 is left as-is
  to avoid applying LayerNorm twice. The baseline therefore has mixed HF
  semantics: layers 5/11 are raw block outputs and layer 23 is normalized.
- Fixed method: RSG4 `fusion_factorial`, same variant, query path, gating,
  fusion, thresholds, postprocessing, and noise guard.
- Dataset/split: MVTec AD 2 `test_public_seen_development`. Query masks and labels
  are used by the evaluator only, never support fitting or prediction.
- Backbone: frozen `camenduru/dinov3-vitl16-pretrain-lvd1689m`, feature layers
  [5, 11, 23], short edges [448, 672, 896, 1120], seed 0.
- Support: the same fixed 16-shot `configs/methods/VOID_support_16.json`
  manifest in both arms. Preprocessing, warmup, and evaluator are unchanged.
- Primary metric: macro AUPRO@0.05; secondary: pAUROC@0.05; F1-oracle remains a
  diagnostic. Higher is better; differences are reported in percentage points.
- Initial screen: can, fabric, walnuts (6 class-arm evaluations). Expand to the
  remaining five classes only if at least one paired class or the three-class
  macro changes by >=0.86 pp in AUPRO. This is a development screening rule,
  not a significance claim or a causal threshold.
- Maximum budget: 16 class-arm evaluations (full8 × two arms), using at most
  four already assigned dsba3 GPUs. Within each class lane the raw and
  normalized configs run sequentially with distinct output roots. One retry is
  allowed for a safe runtime failure; stop after a repeated failure, invalid
  support/config provenance, incomplete/non-finite metrics, or budget
  exhaustion. Maps and weights remain disabled; logs and compact metrics are
  retained.

## Screen-triggered expansion completion

The five remaining classes were evaluated under the allocation above. All 16
planned class-arm evaluations completed with zero recorded runner failures.
The paired manifests match on code hash, support/query protocol, and execution
environment; after removing per-arm output paths, the only scientific config
difference is `backbone_config.normalize_intermediate_features`. Both arms
used the same 16-shot support manifest, query labels were unused, and
predictions were finite with complete coverage.

Full8 macro AUPRO@0.05 was 55.86512 for raw hidden states and 49.20248 for
normalized intermediate features (−6.663 pp). Secondary macro pAUROC@0.05 was
82.35507 and 78.50392 respectively (−3.851 pp). AUPRO decreased on seven of
eight classes; `fruit_jelly` increased by 0.856 pp. Class-level metrics and run
provenance are recorded in
[`results/dinov3_norm_20260929/full8_combined/comparison.md`](../../../results/dinov3_norm_20260929/full8_combined/comparison.md).

## Interpretation boundary

This is a single seed and public development population. Any difference is a
paired observation under this configuration. It does not establish
generalization, a causal normalization effect independent of implementation
details, or private-split performance.
